# 设计说明

本文说明系统由哪些部分组成，每一部分要解决什么问题，以及为什么这样做。读者是想读懂或修改这份代码的开发者。实验结果见 [EXPERIMENTS.md](EXPERIMENTS.md)，评估集的构成与判定规则见 [eval/README.md](../eval/README.md)。

## 1. 目标与不做的事

系统要做到三件事：分层的取数链路能端到端运行，包括路由、三层取数、澄清和兜底；效果可以量化，在自建评估集和 BIRD 基准上给出路由、槽位、执行准确率、延迟与费用；每个关键设计都有实验或测试作为依据。

不做的事情同样明确：不微调模型，不做多候选生成与投票，不做开放式的多轮对话（只支持回答系统自己发起的澄清），不接真实的权限系统（用只读连接和语句护栏模拟），也不做生产部署。

## 2. 数据

数据是 PKDD'99 捷克银行的真实脱敏数据，也就是 BIRD 基准中的 financial 库：8 张表，其中交易表有 1,056,320 笔记录，时间跨度为 1993 年到 1998 年。在它之上，`scripts/build_warehouse.py` 按数仓的方式分三层构建 `data/bank_risk.sqlite`。原始 8 张表原样复制，作为 ODS 层；DWD 层是风险事件表 `dwd_risk_event`，由三条监测规则从交易流水中识别出来；ADS 层是月度指标表 `ads_okr_monthly`，由语义层的编译器物化生成（见第 5 节）。

| 规则 | 条件 | 风险大类 |
|---|---|---|
| LARGE_CASH（大额现金取现） | 现金取现单笔不低于 50,000 | 反洗钱 |
| RAPID_IN_OUT（快进快出） | 单笔入账不低于 30,000，且当日起 3 天内同一账户的出账累计不低于该笔入账的 90% | 反洗钱 |
| OVERDRAFT_PENALTY（透支罚息） | 因余额为负而计收的罚息 | 信用 |

阈值来自数据探查（见 [DATA_PROFILE.md](DATA_PROFILE.md)），例如 50,000 约为现金取现金额的 99.5 分位。构建完成后共有 8,625 条风险事件，月度指标表 3,848 行。

这份数据有几处需要特别处理：交易类型中存在原始文档没有列出的 VYBER；`k_symbol` 的缺失值有 NULL 和单个空格两种写法；区县表的 A4 至 A7 列是以文本存储的数字。为了让"上个月""今年以来"这类说法的结果可复现，参考日期固定为数据的最后一天 1998-12-31。

## 3. 语义层

语义层由 `semantic/` 下的三份 YAML 组成，是系统中唯一定义"指标怎么算、维度在哪里、表怎么关联"的地方。第一层的物化、第二层的编译、第三层注入的口径说明、口径问答的回答，全部由这三份文件生成，所以同一个指标在不同路径上不会出现两种口径。

`catalog.yaml` 是物理字典：每张表的中文名、粒度、说明、注意事项，每个字段的类型、中文名和说明，以及外键关系。第三层的表结构文本、检索文档和外键关系图都从这里生成。

`dimensions.yaml` 定义三样东西。第一是关联图，只包含多对一方向的边，编译器只沿这些边寻路，所以从构造上就不会因为 JOIN 而重复计数；"账户所有人"通过把权限关系表限定为 `type = 'OWNER'` 的别名表达，保证与账户一一对应。第二是日、月、季度、年四种时间粒度的 SQL 写法。第三是 12 个维度，每个维度说明它在哪一列，以及每个取值的编码、中文名和别名；别名就是值链接的词典。

`metrics.yaml` 定义 18 个指标，其中 9 个是需要物化的月度指标。每个指标写明基表、统计时间列、聚合方式、口径条件和单位。聚合方式有四种：`count` 和 `sum` 可以跨月相加；`count_distinct` 不可加，月值不能累加成季度值；`ratio` 由分子、分母两个可加指标构成，汇总时分别求和再相除。文件末尾的 `ambiguous_terms` 列出多义词（例如"损失"可以指不良贷款金额，也可以指风险涉及金额），命中时系统发起澄清，不替用户选择。

## 4. 一次请求的处理

`Text2SQLAgent.ask`（`pipeline/workflow.py`）是唯一的入口：先路由，再根据路由结果交给一个处理分支，分支包括第一、二层、第三层、口径问答、域外引导和澄清。每一步都记录名称、说明和耗时，命令行的 `--trace` 和界面的链路详情显示的就是这份轨迹。返回的 `AgentResponse` 包含答案文本、原始结果与格式化后的结果、执行过的 SQL、IR、澄清类型与候选、代码替用户做的全部假设、轨迹和模型用量。任何阶段的模型调用失败，都会在这里转成一条写明原因的回答，而不是让异常中断会话。

## 5. 路由

路由（`pipeline/router.py`）分三步：规则、一次结构化解析、确定性规范化。最后统一检查所问时间是否在数据范围内。

### 5.1 规则

规则（`pipeline/rules.py`）依次判断口径问答、与数据无关、多义词和模糊时间，最后尝试快速通道。原则是规则可以不判，但不能判错：判错会直接给出错误答案，不判只是多一次模型调用。

判断"与数据无关"要求问题里既没有业务词，也没有"多少""趋势"这类取数词。业务词表由语义层中的指标、维度、取值的名称与别名自动生成，再加上少量通用业务词。快速通道只接受一个指标、可选的时间和地区：把这三部分从问题中去掉之后，剩下的只能是"请问""是多少"这类虚词，有任何实义词都交给模型。快速通道只识别地区，因为在扩大到全部维度的实验中，新增覆盖的问题全部解析错误（例如"每月"被当成"按月出账单"）。

### 5.2 结构化解析

其余问题由模型做一次结构化解析（`pipeline/parser.py`）。系统提示列出全部指标和维度、多义词说明、解析规则和 8 个示例，内容固定不变，以便服务端缓存前缀。模型按以下顺序输出：意图、指标、时间原文、维度、筛选条件、查询类型、粒度、对比方式、排序与数量，最后是判断（`covered`、`uncovered`、`clarify`）和理由。判断放在最后，是因为模型逐字生成，后写的内容才能参考先写的内容。

回复用 Pydantic 校验：结构要对，指标和维度编码必须在语义层中，`limit` 至少为 1，取数问题必须给出判断，能表达的问题必须给出查询类型。只校验结构是不够的：负数 `limit` 在 SQLite 中等于不设上限，编造的指标编码会被误当成"语义层表达不了"。校验不通过时，把逐条错误说明发回模型重试一次；第二次仍不通过，就请用户换一种说法。

### 5.3 规范化与 IR

规范化（`pipeline/normalize.py`）把解析结果翻译成 IR，也就是只描述业务意图、不涉及物理实现的查询表示：

```python
class QueryIR(BaseModel):
    metrics: list[str]                    # 指标编码，至少一个
    query_type: Literal["point", "breakdown", "trend", "compare"]
    time_range: tuple[date, date] | None  # 闭区间；None 表示不限时间
    grain: Literal["day", "month", "quarter", "year"] | None   # 趋势查询必填
    dimensions: list[str] = []            # 分组维度
    filters: dict[str, list[Code]] = {}   # 维度到已链接的库内编码
    compare: Literal["yoy", "mom"] | None = None
    order: Literal["desc", "asc"] | None = None
    limit: int | None = None
```

时间以谁为准取决于问题能否被语义层表达。能表达时，问题中的时间只可能是统计期间，所以以规则从原文解析的结果为准，原文有多个时间时才由模型的摘录来挑选；表达不了时，日期可能是筛选条件（例如出生年份），只把模型的摘录换算后交给第三层作为提示。时间解析（`semantic/timeparse.py`）按固定顺序匹配规则：上个月、上季度、去年按自然周期计算；"近 N 个月"包含当月；两位年份取离参考年份最近的世纪；整月区间的环比基期按月平移，其余按天数平移；"最近""目前"这类说法不猜，转为澄清。

筛选值通过值链接映射为库内编码（`semantic/linker.py`）：先按规范化后的字符串等值匹配中文名、别名和编码，不中时才做模糊匹配，并且只接受唯一最优且相似度不低于 0.85 的结果，同时在答案中注明。如果某个值在模型给出的维度里链接不上，就在指标可达的维度里查找，唯一命中则纠正并注明，否则转第三层。

另外三种情况也在这里处理。指标自带的条件与同一列上的用户筛选没有交集时（例如"现金取现笔数"加上"信用卡取现"的筛选），结果必然为 0，转为澄清；逐期对比（"每月相对上月"）超出单期 IR 的表达能力，转第三层；趋势粒度、对比方式、排序方向等缺省值由代码补上，并写进答案。最后，完全超出数据范围的时间转为澄清，部分重叠的裁剪并注明，基期超出范围的注明无法计算变化率。这项检查放在快速通道与模型解析的汇合点，任何路径都不能绕过。

## 6. 第一层与第二层

第二层的编译器（`semantic/compiler.py`）把 IR 编译成参数化 SQL。指标按基表分组，每张基表生成一条查询，多条查询的结果再按维度合并，这样不依赖各个引擎支持程度不一的 FULL OUTER JOIN。SQL 由 `semantic/templates/` 下的四个 Jinja2 模版生成，分别对应单值、分组、趋势和对比，FROM、JOIN、WHERE 部分共用一个片段。用户的取值与日期只以参数形式出现。所有指标的口径条件相同时放进 WHERE；不同时每个指标用自己的条件聚合。比率指标用分子之和除以分母之和，分母为 0 时返回 NULL，避免把"没有放款"显示成"不良率 0%"。对比查询一次扫描同时覆盖本期与基期，输出本期、基期、变化量和变化率。

第一层是月度指标表。`semantic/okr.py` 的 `l1_ineligibility` 依次检查五个条件，全部满足才查这张表：指标都已物化；维度和筛选都只涉及地区；粒度不细于月；时间范围按整月对齐（对比查询的基期也要对齐）；去重计数类指标只能按月取值，或只涉及单月，并且不能同时筛选多个地区。最后一条最容易出错：1997 年第四季度的风险账户数，三个月的月值相加是 438，按账户去重只有 333。

月度指标表由 `materialize_okr`（`semantic/materialize.py`）生成：对每个月度指标构造"按月"和"按月、按地区"两个 IR，用第二层的编译器执行后写入。表是长表（月份、地区、指标编码、指标值、分子、分母），新增指标只加行，不改表结构；没有数据的单元格不写入，与第二层"分组只列出有数据的组"保持一致。每次构建都在一个事务中全量重建，失败时保留旧表。测试逐项比对两层在 9 个指标、6 种查询形态上的结果。

## 7. 第三层

第三层（`pipeline/layer3.py`）处理语义层表达不了的问题。每个问题先组织上下文，然后循环执行：生成、校验、干跑、执行，失败就按错误类型处理。

上下文由几部分组成。表结构默认来自检索：用 BM25 和本地向量模型分别对表文档打分，按名次做 RRF 融合（第 r 名得 1/(60 + r)），取前 5 张表，再按外键关系图补上它们之间最短路径上的桥接表。向量模型默认是多语言的 bge-m3（官方 ONNX 导出，经 fastembed 加载，输入截断到 512 个 token，向量按文本缓存在磁盘上）；也可以换回纯中文的 bge-small-zh-v1.5，这时表和字段的检索对不含中文的问题只用 BM25，因为该模型对英文的排序是噪声，而示例选择始终用融合，示例库全是中文问题。BM25 对英文词去掉复数词尾，问题里的 accounts 才能匹配到文档里的 account。只提供关联键的表（如账户表、权限关系表）问题里很少提到，不补的话常常写不出 JOIN。每张表一篇检索文档，内容是表名、中文名、说明、粒度、全部字段名与中文名，以及 BIRD 的英文字段说明；实测在这份文档里再加入字段说明和维度取值，反而因为稀释了表的特征词而降低召回。表结构之外，上下文还包括问题涉及指标的官方口径、链接器在问题中识别出的取值与对应编码（例如"取现"对应 `trans.operation = 'VYBER'`）、按相似度从 10 个手写示例中选出的 3 个，以及问题原文、外部知识和已换算的统计期间。

生成的输出是包含 `sql` 和 `explanation` 两个字段的 JSON，`explanation` 会写进答案。执行失败后的处理如下：

| 错误类型 | 处理 |
|---|---|
| 语法错误、类型错误、其他错误 | 带着报错和上一版 SQL 重写 |
| 字段不存在、字段有歧义 | 重写，并把表结构扩大到全部表，因为需要的表可能没有被检索到 |
| 护栏拒绝（多条语句、FROM 中有函数、字典外的表） | 带着拒绝原因重写 |
| 超时 | 提示缩小时间范围、补充筛选、避免笛卡尔积后重写 |
| 表不存在、写操作、非查询语句 | 不重写，直接返回失败 |
| 结果为空 | 不重写，返回结果并提示核对筛选条件 |

最多修复 3 次。结果为空不修复，是因为确实存在本该为空的问题，自动修复可能把正确的查询改错。这个取舍有代价：强模型在信息不足时会写出结果必然为空的占位查询，它不会触发修复，也就不会触发表结构的扩大。

第三层的各个部分都做成了开关（`Layer3Options`）：表结构来源、检索方法、候选表数量、示例数量、是否注入口径与取值、修复次数上限，以及下面三项 Schema Linking 增强，默认值就是线上配置。实验中，在 8 到 10 张表的规模下，全量表结构与各种检索方式的准确率相同；默认保留检索，是为了表多到放不下时可以直接扩展。

### 7.1 Schema Linking 增强

表结构变大以后，固定取前 5 张表的检索会漏表，交给模型的无关字段也会变多。为此第三层另有三项可以单独打开的增强，默认都关闭。

字段级链接（`column_linking`）做三件事。第一，为每个字段建一篇检索文档（表名、字段名、中英文名、说明和编码含义），按问题给字段排序，排序结果供选表和裁剪参考。第二，为数据库中低基数的文本列建取值索引（`knowledge/values.py`）：只收不同取值不超过 1,000 个、含字母的取值，抽样表按全表的不同取值数判断；问题与外部知识中按整词出现的取值算命中，专有名词要求首字母大写，3 个字符以内的全大写代码要求大小写一致，拼写稍有出入时用字符三元组相似度匹配（唯一最优且不低于 0.8，并标明是模糊匹配）。第三，问题中出现语义层的维度名或别名（例如"地区"）时，取该维度所在的字段。取值和维度所在的表并入候选，再一起做连接补全，提示词中写明每个取值所在的字段。

模型选表（`table_selection`）在检索之后多调用一次模型。模型只看到每张候选表的卡片（表名、中文名、说明、字段名与中文名）和链接结果，返回需要保留的表名和理由；它只能删表，不能加表。代码丢弃候选之外的表名，再按外键关系补回连接所需的中间表；模型调用失败、拒答、输出不合格或一张都没选时，沿用原候选。

模型裁剪字段（`column_pruning`）在选表之后再调用一次模型。模型看到最终几张表的完整字段说明，返回需要的字段；主键、外键以及取值和维度所在的字段由代码强制保留。生成只看到保留下来的字段；生成的 SQL 因字段不存在或有歧义而报错时，取消裁剪并改用全量表结构重试；裁剪失败时不裁剪。

候选表数量（`top_k`）默认是 5。实验 X6 在混入 67 张干扰表、共 75 张表的环境中比较了这些配置，结论见实验报告：大表结构下的主要瓶颈是检索召回，取值命中扩表、检索修正和多语言向量模型带来了确定的提升（所需表全部进入上下文的题从 7.5% 升到 52.8%）；模型选表和裁剪能把交给生成模型的上下文压缩到原来的几分之一，所需表的覆盖基本不变，候选池放大时还比直接交给模型更便宜，但没有带来额外的准确率。

## 8. 执行与安全

执行器（`db/executor.py`）每次执行都新建只读连接（URI 中的 `mode=ro`，加上 `PRAGMA query_only = ON`），写操作会在数据库内部被拒绝。超时通过进度回调实现，每 1 万条虚拟机指令检查一次截止时间；结果最多取上限加 1 行，多出的一行用来判断是否截断。展示时上限为 1,000 行，评估时为 5 万行（BIRD 有金标结果多达 15,140 行）。干跑使用 `EXPLAIN QUERY PLAN`，只编译不执行，它能发现语法错误、表或字段不存在，但发现不了口径错误。失败时按报错文本归类为错误类型，修复循环据此决定是否重写。

只读连接挡不住所有风险：ATTACH 可以新建文件，VACUUM INTO 在失败前就创建了目标文件，读取 `sqlite_master` 能拿到全部表结构。所以第三层的 SQL 在执行前还要经过语句护栏（`db/guard.py`）。护栏用 sqlglot 解析语法树，只放行已知安全的语句：恰好一条查询（SELECT 或集合运算，可以带 WITH），FROM 中没有函数，引用的表（CTE 名除外）全部在字典内。非查询语句直接拒绝，其余违规带着原因交给模型重写。最外层没有 LIMIT、LIMIT 为负或超过上限时，改写为上限加 1，这同时让 SQLite 在排序时只保留前若干行。

生产环境还需要在此之上加三件事：以提问人的身份和权限执行，用列级权限或脱敏视图处理敏感字段，并保留审计日志。

## 9. 答案

第一、二层的答案包括一句结论、路由、时间范围与数据截止日期、每个指标的口径、筛选条件，以及代码做的全部假设。第三层的答案注明"非标准口径，请结合 SQL 核对"，并附上模型对口径的说明。对比查询的基期如果在数据范围之前，基期显示"无数据"，变化率显示"无法计算"，原始结果中保留 0 供评估使用。

分组、趋势以及多行的第三层结果，第一句由模型总结（`pipeline/summary.py`），不超过 60 字。总结中出现的每个数字都必须能在结果表或问题原文中找到（去掉千分位后按数值比较），否则退回"共 N 行结果，见下表"；结果超过 100 行或者没有配置模型时不生成总结。这个检查有已知的漏洞：计算结果恰好等于表中某个数时查不出来，中文数字也不在检查范围内。

澄清分两类。指标多义时给出候选指标和各自的口径；时间有问题时说明原因，并给出写法示例。用户的回答会被改写进原问题，再完整地重新执行一遍：选中的指标名替换多义词，用户给出的时间替换问题中规则能识别的时间表达和模糊时间词，原问题没有时间时加在句首。命令行和界面最多接受 3 轮追问。

## 10. 模型接口与成本

所有模型调用都经过同一个接口 `complete(system, user, schema, purpose)`（`llm/base.py`），厂商差异封装在各自的客户端里，服务端和网络错误统一转成 `LLMError`。`purpose` 决定推理强度：解析和总结用低强度，第三层生成用中等强度。DeepSeek 客户端使用 JSON 模式和温度 0，回复为空时再请求一次。Claude 客户端用 `output_config.format` 做结构化输出，用 `effort` 控制推理强度，不发送温度；拒答只记录为拒答，不回退到其他模型，这样模型对比测到的始终是指定的模型。

费用按 `eval/cost.py` 中的价格表计算，区分缓存命中的输入、未命中的输入和输出。DeepSeek 一律按高峰价计算，作为上限；Claude 的缓存写入加价没有计入，费用略有低估。系统提示保持不变以利用前缀缓存，缓存命中的价格只有未命中价格的 2%。

## 11. 评估

自建评估集（`eval/domain_eval.yaml`）有 101 题，在开发前冻结，按类别内的序号划分为开发集 41 题、测试集 60 题；BIRD financial 有 106 题，在原始的 8 张表上评测；实验 X6 另外构建了大表结构环境（`scripts/build_distractors.py`），把 BIRD dev 其余 10 个库的 67 张表作为干扰混入，每张表最多 1,000 行，字段说明由 BIRD 自带的说明自动生成，题目与金标不变，评估脚本加 `--distractors` 即可切换。`scripts/run_eval.py` 有四种模式：`full` 是端到端；`oracle` 给定标注好的 IR，只测第一、二层的编译与执行，不调用模型，用来定位误差出在理解还是编译；`all-l3` 把所有取数题直接交给第三层，配合 `--variant` 做消融；`naive` 是朴素基线，只给全量表结构，一次生成，不检索、不给示例、不修复。

每次运行把逐题记录（路由、IR、SQL、结果、错误、延迟、调用次数、token、费用和完整轨迹）和汇总指标写入 `runs/<name>/`。指标包括路由准确率与混淆矩阵、两种口径的执行准确率、可执行率、槽位准确率、IR 完全一致率、澄清的精确率与召回率、延迟、调用次数与费用。自建集的执行准确率允许额外的说明列，只有要求排序的题比较行序；BIRD 使用官方的结果集严格比较。

实验报告中的表格由 `scripts/summarize_runs.py` 和 `scripts/compare_runs.py` 写入 `<!-- X1:BEGIN -->` 与 `<!-- X1:END -->` 这样的标记之间，不手工修改。由于温度为 0 的模型输出仍会波动，每组实验运行 3 轮；测试集的首次结果作为正式成绩，之后的修改单独报告。

## 12. 配置、测试与扩展

配置从 `.env` 读取（模版为 `.env.example`）：

| 变量 | 默认值 | 作用 |
|---|---|---|
| `LLM_PROVIDER` | deepseek | 默认的模型提供方 |
| `DEEPSEEK_API_KEY`、`ANTHROPIC_API_KEY` | 无 | 密钥 |
| `DEEPSEEK_MODEL`、`CLAUDE_MODEL` | deepseek-flash、claude-sonnet-5-5 | 模型 |
| `DEEPSEEK_THINKING_FOR_GENERATE` | 0 | 为 1 时第三层生成开启 DeepSeek 思考模式 |
| `SQL_TIMEOUT_S` | 10 | 单条 SQL 的超时秒数 |
| `MAX_ROWS`、`EVAL_MAX_ROWS` | 1000、50000 | 展示与评估的行数上限 |
| `MAX_REPAIR_ATTEMPTS` | 3 | 第三层最多修复次数 |
| `EMBEDDING_MODEL` | bge-m3 | 检索用的向量模型：bge-m3（多语言，约 2.3 GB）或 bge-small-zh（中文，约 90 MB） |

测试用 `uv run --group dev pytest -q` 运行，共 417 项，不调用真实模型：需要模型的地方用 `tests/scripted_llm.py` 中按顺序返回预设回复的假模型代替，缺少数据库或向量模型时相关测试自动跳过。有一项标为 slow 的测试会逐条执行护栏改写前后的金标 SQL，需要用 `-m slow` 单独运行。

新增一个指标的步骤：

1. 在 `metrics.yaml` 中写明名称、别名、基表、时间列、聚合方式、口径条件和单位；需要物化时设 `okr: true`。
2. 如果涉及新的表或维度路径，在 `dimensions.yaml` 的关联图中补上多对一的边。
3. 运行 `scripts/build_warehouse.py` 重建月度指标表。
4. 运行测试，并在 `tests/test_compiler.py` 中为新指标补一条独立手写的金标 SQL。

解析提示和口径问答都从 YAML 自动生成，不需要改代码。新增取值或别名只需改 `dimensions.yaml`；一个说法对应多个指标时，把它加入 `ambiguous_terms`。新增模型提供方需要实现 `complete`、把错误包装为 `LLMError`、在 `get_llm` 中注册，并在 `eval/cost.py` 中加入价格。迁移到 Hive、Spark SQL 这类离线数仓引擎时，语义层、路由、IR 和编译流程不变，需要改的是执行器（异步提交、轮询与取消）、干跑方式（执行计划与扫描量估算）、时间条件（落为分区过滤，并区分参考日期与数据截止日期）和模版中的方言写法。

## 13. 已知局限

路由是端到端失败的主要来源。第三层在计算环比时，模型可能在窗口函数的同一层用 WHERE 筛选输出期间，把基期一起筛掉。强模型的占位查询会绕过修复和表结构的扩大，目前还没有识别。模型总结的数字校验存在前面提到的漏洞。时间追问的改写在原问题有多个时间时，可能留下多余的连接词。语义层的口径与取值注入依赖中文名称识别，对英文问题不起作用；英文问题中按原样出现的库中取值由取值索引识别，但表很多时，常用英文词与干扰表中的取值撞上的情况明显增多。bge-m3 比原模型大得多，在 CPU 上为大表结构的 75 篇表文档计算向量约需 30 秒，向量缓存在磁盘上之后不再重复计算。
