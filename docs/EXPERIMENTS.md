# 实验报告

本报告用六组实验评估这个系统。X1 在开发前冻结的 60 道测试题上做端到端评估，执行准确率 93.8%，三轮结果一致；语义层路径全部正确，答错的题都出在路由上。X2 把同一批题交给模型直接写 SQL：忽略输出格式的差异后，数值正确率并不低于分层，但多轮之间的结果更不稳定，遇到多义问题也不会追问。X3 在 BIRD financial 上对生成路径做消融，示例贡献约 4 个百分点，修复约 1 个百分点。X4 比较全量表结构和三种检索方式，各方式能召回的表差别很大，执行准确率却处在同一水平。X5 换用 Claude Sonnet 5.5：在自建测试集上与同一份代码的 DeepSeek 相当，在 BIRD 的生成路径上高约 5 个百分点；同时发现，强模型在信息不足时会写出结果必然为空的占位查询，绕过了依靠报错触发的修复。X6 把 BIRD 其余 10 个库的 67 张表混入作为干扰，在 75 张表上，原来的检索只能让 7.5% 的题拿到全部所需的表，执行准确率从 20.8% 降到 14.2%；字段级链接把它提到 18.9%，修正英文检索之后基线回到约 20%；换用多语言向量模型 bge-m3 后，所需表齐全的比例升到 52.8%，基线为 21.7%。模型选表和裁剪能把交给生成模型的上下文压缩到原来的几分之一，但没有带来额外的准确率。

各节中位于 `<!-- Xn:BEGIN -->` 与 `<!-- Xn:END -->` 之间的表格由脚本从运行结果生成，复现方法见最后一节。

## X2 分层与直接生成

这组实验回答：为什么不把所有问题都交给模型直接写 SQL。

在这个规模（10 张表，表说明比较完整）下，直接生成的数值正确率与分层相当。两个对照组的执行准确率更低，主要是因为输出形式与金标不同；把格式差异视为正确后，它们分别为 95.8% 和 97.2%，分层的正式成绩是 93.8%，丢掉的分全部来自 X1 中那 3 道路由错误的题。这与外部基准中"语义层明显好于直接生成"的结论并不完全一致：单题准确率不是语义层在这个规模下的主要价值。

语义层的价值在可靠性上。同一个问题每次生成同一条 SQL、得到同一个结果；口径和相对时间由代码保证，而直接生成时模型会用真实的当前日期计算"上个月"，结果为空；对比类问题总是给出本期、基期、变化量和变化率；遇到多义问题会追问，两个对照组则对 6 道应当澄清的问题全部自行选了口径。代价是路由会出错，并且多了解析和总结两次调用，取数题的延迟中位数约为直接生成的 1.6 倍，每题费用在同一量级。

对照组在语义层能表达的题上，错误主要有三类。一是相对时间：模型用 `DATE('now')` 推算"上个月"，或者对"近三个月"的理解与约定不同，而分层路径用固定的参考日期由规则换算。二是分组粒度：例如"1998年各地区的现金取现金额"，同一第三层组按区县而不是地区分组。三是输出形式，即上面列出的 5 道题，数值正确，只是形式与金标不同。

示例是有效的：去掉示例后执行准确率下降约 4 个百分点，三个难度上都有下降，而费用和延迟不变。修复的收益则很小：约 8% 的题次需要修复，25 次修复只修好 2 次，总体只提高约 1 个百分点。去掉修复时每轮约有 8 道题执行报错；加上修复后这些题都能执行了，但大多仍然答错。原因是 BIRD 上的失败绝大多数是"能执行但答案不对"，干跑和执行都发现不了，修复能修的是报错，而不是错误的口径。修复只在报错时才触发，每题平均多出约 0.08 次调用，所以仍然保留。

绝对水平需要结合评测口径来看。困难题 57 道中有 50 道的金标结果超过 5 列，大多是"提供某某的综合画像"这类开放式问题，失败也多为列数与金标不同；严格比较要求结果集完全一致，相当于要猜中标注者选了哪些列，困难题几乎无法得分。简单题和中等题（金标不超过 5 列）上，完整第三层约为 43%。本结果只用了 2025-11 清洗版的 financial 单库，第三层默认也只取检索到的表，不能与 BIRD 榜单直接比较；表结构的影响见 X4。

稳定性方面，完整第三层 3 轮中结果完全相同的题为 66/106，明显不如语义层路径（X2 中为 48/48）。另有一项没有测试：DeepSeek 的思考模式在这组题上每题约需 70 秒（其他配置约 2 秒），对交互场景不现实，开跑后即中止。

第一层和第二层不受模型影响，两个模型在这两层都是 100%，因为这两层的 SQL 由语义层模版生成，模型只负责解析。自建测试集上，Claude 的单轮成绩为 97.9%，应当与同一份代码上的 DeepSeek（事后修复版本，98.6%，三轮在 97.9% 至 100% 之间）比较。本报告的早期版本把它与修复前的正式成绩 93.8% 相比，把 4 个百分点的差距归因于模型，这是错误的：其中 L3-10 是靠事后修复加入的规则答对的（问题提到语义层没有覆盖的表时直接转第三层），轨迹中写明了这一点，与模型无关。在同一份代码上，两个模型只在两道题上表现不同：L3-02 Claude 答对，DeepSeek 三轮中只答对一次；L3-15 Claude 写出了占位查询，DeepSeek 答对。因此在自建集上，换用 Claude 没有带来可以确认的提升，路由准确率分别为 100% 和 98.9%。在 BIRD 上，默认检索时 Claude 为 27.4%，比 DeepSeek 高约 5 个百分点，提升集中在简单题和中等题；困难题仍是个位数，失败构成仍以列数与金标不同为主。这组比较绕过了路由，不受事后修复的影响。

代价是费用和延迟。自建集每轮费用从 0.016 美元升到 0.286 美元，约 18 倍，延迟中位数从 1.59 秒升到 3.34 秒；BIRD 每轮费用从 0.063 美元升到 1.265 美元，约 20 倍。X5 的全部运行（含试跑与诊断）共约 3.15 美元。

这组实验最重要的发现是占位查询。Claude 在信息不足时不编造字段，而是写出一条能执行、结果必然为空的查询，在说明里写明字段只是占位。BIRD 上有两例：BIRD-103 检索漏掉了客户表和区县表，SQL 为 `SELECT 1 WHERE 0`；BIRD-113 漏掉了卡表，其中一列写成 `WHERE 1 = 0`。改用全量表结构后这类查询不再出现，DeepSeek 在 X3、X4 的全部运行中也从未出现过。第三层只在"字段不存在"等报错时才扩大到全量表结构，空结果按设计直接返回并附上说明，所以这种失败方式绕过了补表机制：默认检索下 Claude 触发修复 0 次，DeepSeek 3 轮共 25 次，其中 21 次扩大了表结构。自建集的 L3-15 表结构完整，也出现了占位查询：为分析这道题另外重跑了 3 次（不改动正式成绩），连同正式运行共 4 次，其中 3 次首次生成的就是占位查询，有 2 次因为占位 SQL 恰好引用了不存在的别名而报错，触发修复后答对。这道题需要先按地区汇总人口再与事件数相除，直接连接会重复累加人口，可见占位查询也会出现在计算较难、模型没有把握的题上。现有的安全网假设"错误会表现为报错"，这对更强的模型不再成立。可行的修复有两种：在生成输出中增加"信息不足"的信号，或者把恒假条件识别为可修复的错误，两者都触发扩大表结构；目前都还没有实现。

改用全量表结构后，Claude 为 31.1%，净多答对 4 题，而 DeepSeek 在 X4 中两种方式相同。但多答对的题主要不在漏表组：漏表的 33 题中有 27 题是困难题，即使给了全量表结构，Claude 也只答对 3 题（默认检索为 2 题），失败原因仍然是列的选择。因此补表机制失效对准确率的实际影响约为 1 题，它的主要意义在于暴露了一个设计假设。这 4 题的差距来自单轮运行，Claude 自身的波动没有测，不足以据此修改默认配置。

对设计的含义是：分层链路让测试集中第一、二层 30 道题的正确率与模型无关；在自建集上，换用更强的模型并没有超过对路由做的几处修改，而这些修改的成绩是看过测试集之后得到的，本身偏乐观。更强的模型的收益主要体现在 BIRD 的生成路径上（约 5 个百分点），代价是约 18 到 20 倍的费用和约 2 倍的延迟。DeepSeek 加分层链路在当前场景下仍是更经济的默认配置；只在解析不确定或第三层失败时才调用强模型，是一个可行的方向，尚未实现。

## X6 Schema Linking 增强与大表结构

这组实验回答三个问题：表结构很大时，检索还能不能找到所需的表；字段级链接、模型选表和模型裁剪字段各自能补回多少；这些增强在原来的小表结构和中文题上会不会变差。

大表结构环境由 `scripts/build_distractors.py` 构建：把 BIRD dev 其余 10 个库的 67 张表混入作为干扰，每张表最多保留 1,000 行，字段说明由 BIRD 自带的说明自动生成，主键与外键写成字典中的"主键""关联"标注，表本身没有描述。financial 环境因此共有 75 张表，自建库环境共有 77 张业务表；题目与金标不变。三项增强都是第三层的开关，默认关闭。字段级链接为每个字段建检索文档，并对数据库中低基数文本列的取值建索引，命中取值所在的表并入候选，提示词写明取值所在的字段。模型选表在检索之后多调用一次模型，只从候选中删表，连接所需的中间表由代码补回。模型裁剪字段再调用一次模型，代码强制保留主键、外键与取值所在的字段，生成因字段报错时取消裁剪并改用全量表结构。

表多了之后，第三层明显变差。BIRD 的基线从原表结构的 20.8% 降到 14.2%，原因在检索：只有 7.5% 的题，所需的表全部在交给模型的上下文里；剩下的题有一部分靠"字段报错时改用全量表结构"补回。字段级链接是唯一一项超出波动范围的单项提升：问题里出现的库中取值（区县名、编码）把所在的表带进候选，所需表齐全的题从 7.5% 升到 17.9%，执行准确率从 14.2% 升到 18.9%（多答对 5 题），每题费用反而略有下降，因为扩大表结构的重写变少了。

候选池放大到前 20 张后，选表的作用才显现出来。与不选表的对照相比，所需表齐全的比例相当（40.6% 和 37.7%），交给生成模型的上下文却从 25.4 张表、365.7 个字段压缩到 3.8 张表、16.2 个字段；执行准确率为 19.8% 和 18.9%（相差 1 题），每题费用从 0.0032 美元降到 0.0023 美元。宽召回加模型精选，能用更短、更便宜的上下文保持同样的召回，这是大表结构下比固定截断更合理的组织方式。

这些结果说明，大表结构下的主要瓶颈是检索召回，而不是上下文太长。离线诊断也指向同一处：BIRD 是英文提问，而项目使用的向量模型 bge-small-zh 只支持中文，在 75 张表上它的排序没有一题能把所需表全部排进前 5，与 BM25 融合后反而把 BM25 的 30 题拉低到 8 题；BM25 本身又没有词形还原，问题中的 accounts 匹配不到文档中的 account。

### 事后优化

以下改动是看过上面的结果之后做的，属于事后优化，单独报告，不替换上面的成绩。改动都是通用规则，不针对具体题目：

| 改动 | 依据 | 位置 |
|---|---|---|
| 不含中文的问题只用 BM25 排序，不再与向量模型融合 | 向量模型只支持中文，对英文问题的排序是噪声 | `knowledge/retriever.py` |
| BM25 对英文词去掉复数词尾（文档与问题同样处理） | accounts 匹配不到 account | `knowledge/bm25.py` |
| 3 个字符以内的全大写取值必须按原样出现才算命中 | 干扰库中的 BAD、PER、HER 与英文常用词撞上 | `knowledge/values.py` |
| 语义层的维度名与别名（如"地区"）也作为字段级链接：所在的表并入候选，裁剪时强制保留该字段 | L3-29 缺区县表 | `pipeline/layer3.py`、`semantic/linker.py` |

前三项作用于英文问题，第四项作用于中文问题。复数处理和短代码规则在形式上对所有问题生效，离线核对过，自建题的检索结果没有变化（大表结构下前 5 张仍为 29/30）。

检索的修正带来了确定的提升。大表结构下，基线的所需表齐全比例从 7.5% 升到 34.0%，执行准确率从 14.2% 升到约 20%（示例修正前的两轮为 20.8% 和 21.7%，修正后一轮为 19.8%），回到了原表结构的水平。原表结构上前 5 张表全部召回的题从 73 题增加到 83 题，执行准确率却没有提高：修正后两轮为 18.9% 和 20.8%，略低于 X4 中原检索三轮的 21.7% 至 22.6%，差距约 2 题，本组轮数不足以判断是检索修正的影响还是波动。这与 X4 的结论一致：8 张表时召回不是主要瓶颈。

示例选择修正之后，三项全开不再低于基线：原表结构为 20.8% 对 19.8%（各 2 轮），大表结构为 21.7% 对 19.8%（各 1 轮），差距都在 1 至 2 题以内，不足以说明三项增强提高了准确率。确定的是它们对上下文的作用：大表结构下，交给生成模型的上下文从 6.0 张表、91.0 个字段压缩到 3.3 张表、13.3 个字段，所需表齐全的比例反而从 34.0% 升到 38.7%，所需字段的保留率不变；代价是每题多两次模型调用，延迟中位数增加 2.2 至 2.5 秒，每题费用增加 0.0002 至 0.0004 美元。原表结构下压缩同样明显，但选表和裁剪会丢掉少量所需的表和字段（所需表齐全从 78.3% 降到 72.6%，非键字段保留从 94.2% 降到 83.1%）。逐题检查第一轮中三项全开答错而基线答对的题，上下文里所需的表和字段都在，差异来自生成本身；第一轮中裁剪丢掉所需字段的 28 道题里，没有一道是基线答对而三项全开答错的，多数是本来就答不对的多列困难题。

综合两轮结果：对准确率影响最大的是检索，表多时先要保证所需的表能进入候选，取值命中扩表和语言相关的检索修正都在这一层起作用。选表和裁剪的价值在于压缩上下文：候选很多时（例如放大到 20 张表），它们用几分之一的上下文保持同样的召回和准确率，费用也低于把整个候选池交给模型；只有几张表时，它们只增加调用次数和延迟。字段级链接在检索修正之后没有单独重测，它的单项贡献以修正前的 4.7 个百分点为准。三项都保留为开关，默认关闭。自建题上，修正后的维度链接使 L3-29 在三项全开时答对，两组都是 28/30，答错的 L3-15 和 L3-18 是已知的不稳定题和局限。

本组全部真实调用（试点、原始 10 组、第一轮重跑与补跑、修正后的关键组）共约 3.77 美元。修正后的关键组受预算所限只有 1 至 2 轮，结论按此精度理解。

## 复现

先按 README 准备数据和 `.env`。以下运行都会调用真实模型，每题费用见各节表格。每次运行把逐题记录和指标写入 `runs/<name>/`；`--repeats 3` 会生成 `<name>_r1` 到 `<name>_r3`。

```bash
# X1：完整链路，测试集
uv run python scripts/run_eval.py --split test --repeats 3 --name x1_test

# X2：同一第三层与朴素基线（默认只取取数题），以及 6 道应澄清的题
uv run python scripts/run_eval.py --split test --mode all-l3 --repeats 3 --name x2_all_l3
uv run python scripts/run_eval.py --split test --mode naive --repeats 3 --name x2_naive
uv run python scripts/run_eval.py --split test --mode all-l3 --routes CLARIFY --repeats 3 --name x2_all_l3_clarify
uv run python scripts/run_eval.py --split test --mode naive --routes CLARIFY --repeats 3 --name x2_naive_clarify

# X3：BIRD 上的第三层消融
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant full --repeats 3 --name x3_bird_full
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant no-examples --repeats 3 --name x3_bird_no_examples
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant no-repair --repeats 3 --name x3_bird_no_repair

# X4：表结构来源（full-schema、bm25、vector）
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant full-schema --repeats 3 --name x4_bird_full_schema

# X5：Claude（模型名取自 .env 中的 CLAUDE_MODEL，默认为 claude-sonnet-5-5）
uv run python scripts/run_eval.py --split test --provider claude --name x5_test
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --provider claude --name x5_bird
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant full-schema --provider claude --name x5_bird_full_schema

# X6：先构建干扰表（下载 BIRD dev 压缩包，约 346 MB），再跑各组；--distractors 为大表结构
uv run python scripts/build_distractors.py
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant full --name x6_bird_large_base
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant column-linking --name x6_bird_large_linking
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant linking-selection --name x6_bird_large_selection
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant all-linking --name x6_bird_large_all
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant all-linking-k20 --name x6_bird_large_all_k20
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --distractors --variant full-k20 --name x6_bird_large_base_k20
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant full --name x6_bird_small_base
uv run python scripts/run_eval.py --dataset bird --mode all-l3 --variant all-linking --name x6_bird_small_all
uv run python scripts/run_eval.py --mode all-l3 --routes L3 --split all --distractors --variant full --name x6_domain_large_base
uv run python scripts/run_eval.py --mode all-l3 --routes L3 --split all --distractors --variant all-linking --name x6_domain_large_all
```

报告中的表格由三个脚本写入：`scripts/summarize_runs.py` 汇总同一配置的多轮运行（例如 `summarize_runs.py "x1_test_r*" --section X1`），`scripts/compare_runs.py` 在同一批题上比较多个配置，`scripts/eval_retrieval.py` 离线计算检索召回（`--dataset bird --bridged-only --section X4-RECALL`），`scripts/eval_columns.py` 离线计算字段与取值链接（`--section X6-COLUMNS`，加 `--distractors` 为大表结构）。各脚本的用法见文件开头的说明。

需要注意一点：当前代码已经包含 X1 之后的修改，所以现在重新运行 X1，得到的是"事后修复"版本的结果，而不是 93.8% 的正式成绩；修改前的代码没有单独提交过。X6 同理：当前代码已包含 X6 之后的检索修正，重新运行上面的 X6 命令得到的是修正后的结果（报告中修正后的关键组运行名为 `x6q_bird_<small|large>_<base|all>_r<n>`）；X4-RECALL 与 X6-RECALL 等离线表格也是修正前生成的，现在重新生成会得到修正后的数字。向量模型现在默认是 bge-m3；X6 中"事后优化"一节及之前的数字使用 bge-small-zh，复现时设置 `EMBEDDING_MODEL=bge-small-zh`。其余各组实验运行时使用的就是修改后的代码，可以直接复现。另外，模型输出在温度为 0 时也会波动，重新运行的数字会在本报告给出的范围附近变化。
